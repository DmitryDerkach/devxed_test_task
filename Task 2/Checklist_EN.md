## Discount and totals

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PC-01** | A percentage promo code on a cart with one physical item reduces the cart by the percentage of the item amount: SAVE10 (10 %) on one physical item of 50.00 gives discount 5.00.<details><summary><i>Why it matters</i></summary>This is the baseline valid class. If it fails, every customer who uses a promo code sees a wrong price.</details> | HTTP 200; subtotal 50.00, discount 5.00, shipping 0.00 (subtotal ≥ 35.00), total 45.00 = 50.00 - 5.00 + 0.00; message 'Promo code applied successfully'. | EP | 🔴 High | PC-01.1 |
| **PC-02** | A fixed-amount promo code reduces the cart by the fixed amount regardless of the cart value: FLAT5 on a 50.00 cart gives discount 5.00.<details><summary><i>Why it matters</i></summary>A fixed code is the second code type and uses a different calculation branch than the percentage code. | **PC-03** | The subtotal is the sum of count x price over ALL lines: a line with count 2 and price 20.00 contributes 40.00, and several lines of different types are added together (physical 20.00 + digital 30.00 = 50.00).<details><summary><i>Why it matters</i></summary>count must multiply the price (a defect would charge for one unit only), and several lines catch the 'only the last line is counted' bug. Everything else (discount, shipping threshold, total) is built on the subtotal.</details> | 2 x 20.00: subtotal 40.00, discount 4.00 (SAVE10), total 36.00. | **PC-04** | The discount is rounded to cents using the half-up rule, including results smaller than a cent: 10 % of 10.05 = 1.005 is rounded UP to 1.01; 10 % of 0.01 = 0.001 is rounded DOWN to 0.00; and 10 % of 9999.99 = 999.999 is rounded up to 1000.00.<details><summary><i>Why it matters</i></summary>1.005 lies exactly on the rounding boundary (the next digit is 5), so rounding down, truncating or using floating point gives 1.00 instead of 1.01 - one cent lost per order, millions of orders. 0.001 on the lower end checks the same rule from the other side.</details> | 10.05: discount 1.01, shipping 4.99, total 14.03. 0.01: discount 0.00, shipping 4.99, total 5.00. 9999.99: discount 1000.00, total 8999.99. | BVA + EG | 🔴 High | PC-04.1<br>PC-04.2 |
| **PC-05** | A fixed discount is capped by the amount it is applied to and never exceeds it: FLAT5 on a cart of 3.00 gives discount 3.00 (not 5.00), so the goods cost 0.00 at the lowest.<details><summary><i>Why it matters</i></summary>This is the boundary where the discount is greater than the cart. Without the cap the total would be 3.00 - 5.00 + 4.99 = 2.99, i.e. the customer would pay less than the shipping alone and the shop would pay 2.00 out of its own pocket for goods that cost 3.00.</details> | HTTP 200; subtotal 3.00, discount 3.00, shipping 4.99 (3.00 < 35.00), total 4.99 = 3.00 - 3.00 + 4.99. | BVA | 🔴 High | PC-05.1 |

## Promo code

| **PC-19** | A promo code whose usage limit is reached is rejected (USEDUP, 100 uses of 100).<details><summary><i>Why it matters</i></summary>The state 'exhausted' is different from 'unknown' and 'expired' and has its own message. ## Test-design techniques

| Technique | Applied? | Where and why |
|---|---|---|
| **Equivalence Partitioning (EP)** | Yes | Product types (physical / digital / gift_card), code states (valid / unknown / expired / exhausted / blank), code types (percent / fixed), cart compositions. One representative per class where the rule is uniform inside the class. |
| **Boundary Value Analysis (BVA)** | Yes - main technique | Threshold 35.00 (34.99 / 35.00 / 35.01), count 0 / 1 / 999 / 1000, price 0 / 0.01 / 9999.99 / 10000.00, rounding boundary (x.xx5), fixed discount vs. cart value (cap), expiry instant, empty list. |
| **Decision Table (DT)** | Yes - the core of the shipping and gift-card rules | Conditions: code valid \| has non-gift-card items \| digital-only \| subtotal ≥ 35. Outcomes: error / discount + 0 shipping / discount + 4.99. Rows: invalid code → error (PC-17.1, PC-18.1, PC-19.1, PC-20.1, PC-20.2, PC-20.3, PC-21.1, PC-21.2, PC-22.1, PC-20.4, PC-22.2, PC-22.3); only gift cards → error (PC-07.1); digital-only → shipping 0 (PC-12.1); mixed, < 35 → 4.99 (PC-10.1, PC-13.1, PC-08.1); mixed, ≥ 35 → 0 (PC-10.2, PC-10.3, PC-14.1). The ambiguous cell (threshold before/after discount) is isolated in PC-10.2 / PC-11.1. |
| **Pairwise (combinatorial)** | Yes - to pick the mixed carts | Factors: product-type mix (P, D, G, P+D, P+G, D+G) x code type (percent / fixed) x threshold side (< 35 / ≥ 35). Pairwise selected the representative mixed carts (PC-03.2, PC-08.1, PC-09.1, PC-13.1, PC-14.1) instead of the full 24 combinations. |
