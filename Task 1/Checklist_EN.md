## Shipment shape

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PK-01** | A shipment made of exactly ONE item has the item's own parameters: weight, length, width and thickness are copied unchanged (item 1 kg, 10 x 5 x 2 cm → shipment 1 kg, 10 x 5 x 2 cm).<details><summary><i>Why it matters</i></summary>This is the baseline (one item): every other shape rule builds on it, so a defect here makes all other results untrustworthy. It also proves that a cheap but too small packaging is filtered out instead of being picked just because it is the cheapest - a wrong suggestion means an employee packs the goods into a box they do not fit.</details> | The cheapest packaging that really holds 10 x 5 x 2 is suggested: Box-Large 20x10x5 (cost 5). The cheaper Box-Small 9x5x2 (cost 1) is NOT suggested because it is 1 cm too short. | EP | 🔴 High | PK-01.1 |
| **PK-02** | For several items, the shipment length is the largest length among the items and the shipment width is the largest width among the items; the two maxima are taken INDEPENDENTLY, so they may come from different items (items L5 x W9 and L12 x W4 → shipment length 12, width 9).<details><summary><i>Why it matters</i></summary>A typical slip is to take both maxima from the same item (for example, from the longest one) and silently lose the wide item. The packaging would then be too narrow for the real goods, and the customer receives a damaged or unsendable parcel.</details> | A box with inner width 9.00 is accepted; a box identical in everything except inner width 8.99 is rejected. Together they prove the shipment width is 9, not 4 and not 8. | BVA + EG | 🔴 High | PK-02.1 |
| **PK-03** | For several items, the shipment thickness is the SUM of the item thicknesses (not the maximum): items 2 cm + 3 cm = 5 cm. Equality with the packaging thickness is allowed; 0.01 cm less is not.<details><summary><i>Why it matters</i></summary>The sum rule is exactly what distinguishes thickness from length and width, and it is the place where an implementation most easily takes the maximum instead. The exact-fit box is the on-point and the 0.01 thinner box the off-point of the boundary; if either is wrong, stacked orders either fail to fit or are packed too tightly.</details> | The box 10 x 6 x 5.00 (exact fit) is accepted; the box 10 x 6 x 4.99 (0.01 thinner) is rejected, although it is cheaper. The same for two identical items 2 + 2 = 4: box 4.00 accepted, box 3.99 rejected. | BVA | 🔴 High | PK-03.1<br>PK-03.2 |
| **PK-04** | For several items, the shipment weight is the SUM of the item weights and it is compared with the packaging maximum weight; equality is allowed (items 1 kg + 2 kg = 3 kg: limit 3 kg accepted, limit 2.99 kg rejected).<details><summary><i>Why it matters</i></summary>The weight boundary must also work when it is reached by summing several items, not only for a single item (PK-08). Each item alone is below the limit, so only the sum reveals an overloaded packaging that would tear in transit.</details> | Box-Heavy (limit 3) is suggested; Box-Light (limit 2.99, cheaper) is not. | BVA | 🔴 High | PK-04.1 |
| **PK-05** | A single item entered with width greater than length (L3 x W10 x T2) is treated the same as 10 x 3 x 2: the order in which the three dimensions are typed must not change the result, because both the shipment and the packaging are sorted before comparison.<details><summary><i>Why it matters</i></summary>Warehouse staff enter dimensions in whatever order they read them off the label. If the order mattered, the same item would get different packaging depending on who typed it, and a perfectly fitting cheap box would be skipped for an expensive one - money lost on every such shipment.</details> | Box-Exact with inner size 10 x 3 x 2 (cost 1) is suggested instead of the expensive fallback box 30x30x30 (cost 9). | EP + EG | 🟠 Medium | PK-05.1 |
| **PK-06** | A shipment of many items (50 items of 0.1 kg and 0.1 cm thickness) is summed exactly: weight 5.0 kg and thickness 5.0 cm, with no floating-point error (50 x 0.1 in floating point gives 5.000000000000003).<details><summary><i>Why it matters</i></summary>Computers cannot store 0.1 exactly. A 0.000000000000003 excess silently turns an exact fit into a rejection, so the selector would offer a bigger, more expensive packaging for no visible reason. Money and weight calculations must be exact.</details> | The box with exactly 5 kg limit and 5 cm thickness (cost 1) is suggested, not the oversized Box-Big (cost 9). | EG + BVA | 🟠 Medium | PK-06.1 |

## Availability / weight

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PK-07** | A packaging marked as unavailable is never suggested, even when it is the cheapest one and the item fits into it perfectly.<details><summary><i>Why it matters</i></summary>Availability is one of the three conditions of the 'suitable packaging' decision table (available AND weight OK AND size OK). A cheap 'bait' that violates only this condition isolates it: if it is suggested, the employee is sent to take a box that is out of stock.</details> | Box-Cheap (cost 1, 20x10x5, NOT available) is skipped; the next suitable Box-Next (cost 2) is suggested. | EP + DT | 🔴 High | PK-07.1 |
| **PK-08** | The weight limit is an inclusive comparison: shipment weight EQUAL to the packaging maximum weight is accepted (5 kg vs. limit 5 kg), and 0.01 kg above the limit (5.01 kg vs. limit 5 kg) is rejected.<details><summary><i>Why it matters</i></summary>The on-point (equality) and the off-point (0.01 over) of a boundary are where '≤' is most often mistyped as '<'. A strict comparison wrongly refuses a packaging that holds exactly its rated weight; a missing check lets an overloaded packaging through.</details> | 5 kg: Box-Limit (limit 5) is suggested. 5.01 kg: Box-Light (limit 5, cheaper) is rejected and Box-Heavy (limit 6) is suggested. | BVA | 🔴 High | PK-08.1<br>PK-08.2 |
| **PK-09** | When every packaging is unavailable, or the catalog is empty, the result is 'no suitable packaging': an empty result without an error, an exception or an invented default packaging.<details><summary><i>Why it matters</i></summary>These are the empty-result partitions. A crash on an empty catalog would stop the employee's workflow, and inventing a default packaging would hide the real problem (nothing is in stock) behind a fake answer.</details> | Two cases: (a) a catalog of two unavailable packagings, (b) a completely empty catalog. In both, no packaging is suggested and no error is raised. | EP + EG | 🟠 Medium | PK-09.1<br>PK-09.2 |

## Box fit

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PK-10** | A box that is clearly larger than the shipment in every dimension fits (shipment 10 x 6 x 4, box 20 x 10 x 8).<details><summary><i>Why it matters</i></summary>This is the 'valid' equivalence class for boxes - the ordinary happy path. If it fails, the box rule is broken in general, not at a boundary.</details> | Box-Big (cost 3) is suggested; the smaller Box-Small 9x5x3 (cost 1) is rejected. | EP | 🟠 Medium | PK-10.1 |
| **PK-11** | A box equal to the shipment in all three dimensions fits: the comparison is 'box ≥ shipment' (inclusive). Also for a cube: item 5x5x5 into box 5x5x5 (Max = Mid = Min).<details><summary><i>Why it matters</i></summary>Equality must pass, and this is the most commonly broken boundary of the whole task ('>' instead of '≥'). A strict comparison would reject perfectly fitting boxes and push the employee to pay for a bigger one.</details> | Box-Exact 10 x 6 x 4 (cost 2) is suggested instead of the bigger Box-Big (cost 5). Cube: Box-Cube 5x5x5 (cost 1) is suggested instead of the 20x20x20 box (cost 9). | BVA (on-point) | 🔴 High | PK-11.1<br>PK-11.2 |
| **PK-12** | A box that is 0.01 cm too short in ANY single position of the sorted dimensions does not fit: largest (9.99 vs 10), middle (5.99 vs 6) or smallest (3.99 vs 4) - three separate checks, shipment 10 x 6 x 4.<details><summary><i>Why it matters</i></summary>The box check is three independent comparisons (largest-largest, middle-middle, smallest-smallest). Each can be implemented wrongly or forgotten, and only a separate off-point for each position can catch it. A forgotten comparison lets a too-small box through.</details> | In each of the three cases the cheap short box (cost 1) is rejected and the fallback Box-Fallback 10x6x4 (cost 9) is suggested. | BVA (off-point x3) | 🔴 High | PK-12.1<br>PK-12.2<br>PK-12.3 |
| **PK-13** | Box dimensions written in a different order than the shipment's give the same verdict: box typed as (4, 10, 6) for shipment (10, 6, 4) fits, because both sides are sorted in descending order before the comparison.<details><summary><i>Why it matters</i></summary>Sorting both sides is a part of the rule, and comparing 'position by position as typed' is a typical bug. The catalog is maintained by people, and nothing guarantees they write dimensions in the same order as the shipment.</details> | Box-Reordered (cost 1) is suggested instead of the 30x30x30 box (cost 9). | EP + EG | 🔴 High | PK-13.1 |
| **PK-14** | A box with enough VOLUME but one dimension too short is rejected: a long thin item 20 x 1 x 1 does not fit a 10 x 10 x 10 box (volume 1000 versus 20), because 20 > 10.<details><summary><i>Why it matters</i></summary>Comparing volumes is a tempting but wrong implementation: a long rod will never fit a short cube however large its volume is. Wrongly accepted, the rod simply does not go into the box.</details> | Box-Cube (cost 1) is rejected; Box-Long 20x1x1 (cost 5) is suggested. | EG | 🟠 Medium | PK-14.1 |

## Bag fit

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PK-15** | A bag fits when BOTH conditions hold with equality at once: Max + Min = bag length and Mid + Min = bag width (shipment 10 x 6 x 2: Max+Min = 12, Mid+Min = 8; bag 12 x 8 x 1).<details><summary><i>Why it matters</i></summary>Both bag formulas use '≤' ('not more than'), so the exact fit must be accepted. This is the on-point of the bag rule; a strict comparison would refuse the tightest bag that really works.</details> | Bag-Exact (cost 1) is suggested instead of the fallback box 30x30x30 (cost 9). | BVA (on-point) | 🔴 High | PK-15.1 |
| **PK-16** | Each of the two bag conditions, violated alone by 0.01, makes the bag unsuitable: Max + Min = 12 exceeds bag length 11.99, or Mid + Min = 8 exceeds bag width 7.99.<details><summary><i>Why it matters</i></summary>The two conditions are independent. Testing each in a separate case means that a failing case points at exactly one formula, and a forgotten formula cannot hide behind the other one.</details> | Both bags (11.99 x 8 x 1 and 12 x 7.99 x 1) are rejected; the fallback Box-Fallback is suggested. | BVA (off-point x2) | 🔴 High | PK-16.1<br>PK-16.2 |
| **PK-17** | A flat, wide item fits a bag but does not fit a box: item 30 x 20 x 0.5 goes into bag 31 x 21 x 5 (Max+Min = 30.5 ≤ 31, Mid+Min = 20.5 ≤ 21) but not into box 25 x 25 x 25 (30 > 25).<details><summary><i>Why it matters</i></summary>This is the business reason for bags to exist: they accept flat goods that a rigid box of the same size cannot. The case also proves the bag rule is really different from the box rule - if both used the box formula, this would fail.</details> | Bag-Flat (cost 2) is suggested; the cheaper Box-Cube (cost 1) is rejected. | EP + DT | 🔴 High | PK-17.1 |
| **PK-18** | A small thick item fits a bag that is thinner than the item but does not fit a smaller box: item 5 x 5 x 5 goes into bag 10 x 10 x 3 (Max+Min = 10 ≤ 10, Mid+Min = 10 ≤ 10) but not into box 4 x 4 x 4.<details><summary><i>Why it matters</i></summary>The second declared behaviour of bags: the material stretches around a thick item. It shows that the bag's own thickness does not limit the goods, which complements PK-17.</details> | Bag-Soft (cost 2) is suggested; Box-Tiny 4x4x4 (cost 1) is rejected. | EP + DT | 🟠 Medium | PK-18.1 |
| **PK-19** | Item and bag dimensions written in arbitrary order give the same verdict as sorted ones: bag typed as (8, 1, 12) is treated as 12 x 8 x 1; item typed as length 2, width 6, thickness 10 is treated as 10 x 6 x 2.<details><summary><i>Why it matters</i></summary>The bag formulas use Max, Mid and Min, so sorting is required on both sides, exactly as for boxes (PK-13). Without it, the result depends on the typing order and the cheapest bag may be wrongly skipped.</details> | In both cases the bag (cost 1) is suggested instead of the fallback box (cost 9). | EP + EG | 🟠 Medium | PK-19.1<br>PK-19.2 |
| **PK-20** | The bag's third dimension (thickness) is NOT part of the check: a bag 12 x 8 x 0.1 still fits the item 10 x 6 x 2, because only Max+Min ≤ length and Mid+Min ≤ width are compared.<details><summary><i>Why it matters</i></summary>This is our reading of the specification (see assumption 5): the specification compares only length and width of a bag. Locking it in a test turns a silent interpretation into a visible, discussable decision, and catches the accidental use of the thickness.</details> | Bag-Thin (cost 1) is suggested instead of the fallback box (cost 9). | EG (spec reading) | 🟢 Low | PK-20.1 |
| **PK-21** | A too long item fits no bag: item 40 x 1 x 1 against bag 20 x 20 x 20 gives Max+Min = 41 > 20, so the bag is rejected.<details><summary><i>Why it matters</i></summary>It guards against the thought 'a bag stretches, so it holds everything'. Without this negative case, a bag that accepts any item would pass all positive tests unnoticed.</details> | The result is 'no suitable packaging' (empty result, no error). | EP (invalid partition) | 🟠 Medium | PK-21.1 |

## Choosing the cheapest

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PK-22** | When several packagings are suitable, the one with the lowest cost is chosen, and it is neither the first nor the last in the catalog list (costs 7, 3, 5 → the middle one, 3).<details><summary><i>Why it matters</i></summary>This is the core requirement of the whole feature - the cheapest suitable packaging. The cheapest option in the middle of the list rules out implementations that return the first or the last suitable item.</details> | Box-B (cost 3) is suggested, not Box-A (7, first) and not Bag-C (5, last). | EP + DT | 🔴 High | PK-22.1 |
| **PK-23** | If the cheapest packaging is rejected - because it is too small or because it cannot carry the weight - the next cheapest SUITABLE one is chosen (cheapest: 5x5x5 for 1, or limit 3 kg for a 4 kg item).<details><summary><i>Why it matters</i></summary>Filtering must be done BEFORE choosing the cheapest, and each filter condition needs its own cheap 'bait' (size, weight). If the algorithm picks the cheapest first and checks it afterwards, it returns an unsuitable packaging or nothing.</details> | Two cases: (a) Box-Ok (cost 2) is suggested, not Box-Tiny (1) and not Box-Big (3); (b) Box-Strong (cost 2, limit 10) is suggested, not Box-Weak (cost 1, limit 3). | DT | 🔴 High | PK-23.1<br>PK-23.2 |
| **PK-24** | The packaging type must not bias the price comparison: when a bag is cheaper than a box and both fit, the bag is chosen; when a box is cheaper than a bag and both fit, the box is chosen.<details><summary><i>Why it matters</i></summary>A hidden preference for 'boxes first' or 'bags first' would make the selector wrong in one of the two directions. Testing both directions is the only way to see it.</details> | Two cases with swapped prices: Bag-Cheap (1) beats Box-Pricey (2); Box-Cheap (1) beats Bag-Pricey (2). | DT | 🟠 Medium | PK-24.1<br>PK-24.2 |
| **PK-25** | When two suitable packagings cost the same, the one whose name comes first alphabetically is chosen (Box-Alpha before Box-Beta, both cost 4), whatever their order in the catalog.<details><summary><i>Why it matters</i></summary>The specification is silent about ties, and assumption 2 defines the rule. Without a fixed rule, the same input could give different answers on different runs or machines, which makes the feature impossible to test or to trust.</details> | Box-Alpha is suggested although Box-Beta stands first in the catalog. | EG | 🟠 Medium | PK-25.1 |
| **PK-26** | The size of the suitable set is covered: with exactly ONE suitable packaging it is suggested; with NONE (a 50 x 50 x 50 item against packagings of 20 and 30 cm) the result is 'no suitable packaging'.<details><summary><i>Why it matters</i></summary>The partition of the suitable set is 0, 1, many ('many' is PK-22). The cases 0 and 1 are where 'take the first element' and 'take the minimum of an empty list' implementations break.</details> | One suitable: Box-Fits (cost 5) is suggested, Box-TooSmall (cost 1) is not. None suitable: empty result without error. | EP | 🟠 Medium | PK-26.1<br>PK-26.2 |
| **PK-27** | Zero-cost packaging is valid and is the cheapest one: cost 0 is below cost 0.01 (the lower boundary of cost).<details><summary><i>Why it matters</i></summary>Zero is the boundary between valid and invalid cost (assumption 4: cost ≥ 0). A mistaken 'cost > 0' validation would reject free packaging such as the customer's own box.</details> | Box-Free (cost 0) is suggested instead of Box-Paid (cost 0.01); the input is not rejected. | BVA | 🟢 Low | PK-27.1 |

## Invalid input

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PK-28** | An empty list of items (0 items) is rejected as invalid input; a shipment needs at least one item.<details><summary><i>Why it matters</i></summary>Zero items is the boundary below 'at least one'. Silently returning the cheapest packaging for nothing would hide a front-end bug and charge for an empty parcel.</details> | The input is rejected as invalid (an explicit error, not 'no packaging', and no packaging is suggested). | EG + BVA | 🟠 Medium | PK-28.1 |
| **PK-29** | An item whose weight or any dimension is zero or negative is rejected: weight 0, length 0, thickness -1 (valid values are strictly greater than 0).<details><summary><i>Why it matters</i></summary>0 is the boundary between invalid and valid, and a negative number is the typical data-entry error. A negative thickness would even reduce the summed thickness of the shipment and let an oversized stack pass the check.</details> | In each of the three cases the input is rejected as invalid and no packaging is suggested. | BVA + EG | 🟠 Medium | PK-29.1<br>PK-29.2<br>PK-29.3 |
| **PK-30** | A packaging with a negative cost in the catalog is rejected as invalid input (cost -1).<details><summary><i>Why it matters</i></summary>Bad catalog data must not win the 'cheapest' comparison: a negative cost is always the minimum, so such a packaging would be suggested for every shipment it fits.</details> | The input is rejected as invalid; the broken packaging is never suggested. | EG | 🟢 Low | PK-30.1 |

## Statelessness

| ID | What is checked | Expected result | Technique | Priority | Test cases |
|---|---|---|---|---|---|
| **PK-31** | The selector keeps no hidden state: the same input twice gives the same answer, the lists passed in are not changed, and an availability flag switched between calls is reflected immediately (Cheap available → Cheap; not available → Next; available again → Cheap).<details><summary><i>Why it matters</i></summary>The algorithm should be a pure function: the only 'state' is availability and it is an input. A cache or a modified input list would make the answer depend on the history of calls, and the stock changes all day.</details> | Both first calls suggest Cheap; the item list and the catalog are unchanged; after the switch Next is suggested; after switching back Cheap again. | State Transition (degenerate) | 🟢 Low | PK-31.1 |

## Assumptions

The task says *“if the description lacks some details, make your own assumptions and state them”*. Every gap found while writing the checklist is closed here; the checks that depend on an assumption reference it.

| # | Topic | Open question | Assumption accepted | Affects checks |
|:-:|---|---|---|---|
| 1 | Units and precision | What are the units; how many decimals; is there a tolerance? | Weight in kg, dimensions in cm, cost in currency units. Any number of decimals. Comparisons are exact (decimal arithmetic, no rounding, no tolerance). | PK-06, PK-08, PK-12, PK-16 |
| 2 | Equal price | Which packaging is suggested when several suitable ones cost the same? | The one whose name comes first alphabetically (case-insensitive). The result must be deterministic. | PK-25 |
| 3 | Nothing fits | What is returned when no packaging is suitable? | An empty result: the employee is told that no suitable packaging was found. This is a normal outcome, not an error; no default packaging is invented. | PK-09, PK-21, PK-26 |
| 4 | Input validation | Are zero / negative values allowed? | Item weight and all item dimensions must be > 0; packaging cost ≥ 0 (zero is allowed), max weight > 0, all three dimensions > 0; an empty item list is invalid. Invalid input is rejected, never silently corrected. | PK-27, PK-28, PK-29, PK-30 |
| 5 | Bag rule | Does the bag check model the real stretching of the material? | No. The formulas from the specification are the only rule: Max+Min ≤ length and Mid+Min ≤ width. The third bag dimension (thickness) is not used by the check. | PK-15 ... PK-21 |
| 6 | Several items | Is the stacking rule a simplification (rotation, rearranging)? | Yes, and it is the accepted rule: items are never rotated or rearranged, the shape is computed exactly as specified. | PK-02, PK-03, PK-04 |
| 7 | Packaging weight | Does the packaging's own weight count against the maximum weight? | No. Maximum weight limits the goods only. | PK-04, PK-08 |
| 8 | Number of items | Is there an upper limit of items in one shipment? | No limit; shipments of 1, 2 and 50 items are tested. | PK-06 |
| 9 | Splitting | May an order be split into several shipments when nothing fits? | Out of scope. If nothing fits, the result is 'no suitable packaging'; no split is proposed. | PK-26 |
| 10 | Dimension order | In which order are dimensions entered? | Any order, for items and for packaging. The algorithm sorts them as the specification prescribes (both sides for boxes and bags). | PK-05, PK-13, PK-19 |

## Test-design techniques

| Technique | Applied? | Where and why |
|---|---|---|
| **Equivalence Partitioning (EP)** | Yes | Packaging type (box / bag), availability (yes / no), shipment size (1 / several items), outcome (0 / 1 / many suitable), data validity. One representative per class is enough where the rule is uniform inside the class. |
| **Boundary Value Analysis (BVA)** | Yes - main technique | Every comparison in the specification is inclusive (≥ for boxes, ≤ for bags and weight), so on-point (equality) and off-point (0.01 beyond) are tested for: max weight, each of the three box positions, each of the two bag formulas, cost = 0, 0 items, value 0 of a dimension. |
| **Decision Table (DT)** | Yes | Suitable = available AND weight OK AND dimensions OK. Scenarios isolate each failing condition with a cheap 'bait' packaging (single-fault assumption): N-Y-Y → PK-07.1, Y-N-Y → PK-08.2 / PK-23.2, Y-Y-N → PK-12.1, PK-12.2, PK-12.3 / PK-23.1, Y-Y-Y → the happy paths. Multi-fault rows add nothing for an AND of independent checks. |
| **Error Guessing (EG)** | Yes | Floating-point sums, equal prices, unsorted dimensions, comparing volumes instead of dimensions, empty catalog / empty list, bag thickness accidentally used, 'first item' instead of 'max'. These are the bugs the mutation check in the Java project injects on purpose. |
| **State Transition** | Barely - one degenerate case | The algorithm is a stateless function. The only 'state' is packaging availability and it is an input, not a lifecycle. Covered by PK-31 (availability toggled between calls). Forcing a state model here would be artificial. |
| **Pairwise (combinatorial)** | No | Only three independent conditions: the full decision table has 8 rows, pairwise would not save anything. |
| **Mutation check (suite quality)** | Yes - in the Java project | 16 deliberately broken variants of the algorithm must each be caught by at least one scenario (MutationSanityTest). Shows that the checklist can detect real defects, not only that it passes. |
